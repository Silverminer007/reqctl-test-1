# Technical Specification

## Overview

This requirement creates the initial Rust/axum project skeleton for
`reqctl-test`. The repository currently contains no application code (only
`specs/` and a Go-oriented `.gitignore`). This spec describes the new
Cargo project, its module layout, the configuration-loading mechanism for
the listen port (env var and/or config file, per the approved domain spec),
and the single `GET /` route.

There is no existing code to integrate with — this step establishes the
baseline structure that future requirements will extend.

## Project layout

New files at the repository root:

```
Cargo.toml
Cargo.lock          (generated by `cargo build`/`cargo run`, committed)
config.toml         (example/default configuration file, optional at runtime)
src/
  main.rs           (entry point: load config, build router, run server)
  config.rs         (configuration loading: env var + file + default + validation)
.gitignore          (replaced with Rust-appropriate entries)
```

No existing files are modified except `.gitignore` (replaced wholesale,
since the project is no longer Go-based).

## Dependencies (`Cargo.toml`)

Binary crate, package name `reqctl-test`, edition `2021`.

| Crate | Purpose | Notes |
|---|---|---|
| `axum` | HTTP server/router | latest stable major version at implementation time |
| `tokio` | Async runtime | `features = ["full"]`, as conventional for axum |
| `serde` | Deserialize config file | `features = ["derive"]` |
| `toml` | Parse `config.toml` | latest stable version |

`serde`/`toml` are added beyond the original minimal-example assumption
because the approved domain spec requires reading a structured config file
for the port. No other dependencies (logging, web frameworks beyond axum,
DB drivers, etc.) are added.

## Configuration model (`src/config.rs`)

### Data structures

```rust
#[derive(Debug, Deserialize, Default)]
struct FileConfig {
    port: Option<u16>,
}

pub struct AppConfig {
    pub port: u16,
}
```

`FileConfig` mirrors the on-disk `config.toml` shape:

```toml
# config.toml
port = 3000
```

The file is optional — if it does not exist, it is treated as if it
contained no `port` value (i.e. `FileConfig::default()`).

### Resolution function

```rust
pub const DEFAULT_PORT: u16 = 3000;
pub const PORT_ENV_VAR: &str = "REQCTL_PORT";
pub const CONFIG_FILE_PATH: &str = "config.toml";

pub fn load() -> Result<AppConfig, ConfigError>;
```

`load()` implements the precedence and validation rules from the domain
spec:

1. **Read the config file** at `CONFIG_FILE_PATH` (relative to the working
   directory), if present, and parse it as TOML into `FileConfig`. A
   missing file is not an error; a present-but-unparseable file (invalid
   TOML, or `port` not representable as `u16`) is an error
   (`ConfigError::File`).
2. **Read the env var** `REQCTL_PORT`, if set. If set but not parseable as
   `u16` (0–65535), this is an error (`ConfigError::Env`).
3. **Precedence**: if `REQCTL_PORT` is set and valid, its value is used as
   `port`, regardless of whether `config.toml` also specifies a port (env
   var wins, per the approved domain spec). Otherwise, if `config.toml`
   specifies `port`, that value is used. Otherwise, `DEFAULT_PORT` (3000)
   is used.

### Error type

```rust
#[derive(Debug, thiserror::Error)]  // or a manual Display/Error impl to
                                     // avoid adding thiserror, see below
pub enum ConfigError {
    Env(String),   // e.g. "REQCTL_PORT must be a valid port number (0-65535), got: '...'"
    File(String),  // e.g. "failed to parse config.toml: <toml error>"
}
```

To honor the "no additional dependencies beyond what's needed" guidance,
`ConfigError` is implemented with a hand-written `Display` + `std::error::Error`
impl rather than pulling in `thiserror`. It implements `Display` so
`main` can print a clear, actionable error message.

## Application entry point (`src/main.rs`)

```rust
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let app_config = config::load()?;

    let app = Router::new().route("/", get(root));

    let addr = SocketAddr::from(([0, 0, 0, 0], app_config.port));
    let listener = tokio::net::TcpListener::bind(addr).await?;
    axum::serve(listener, app).await?;

    Ok(())
}

async fn root() -> &'static str {
    "Hello, world!"
}
```

Behavioral notes mapping to the domain spec / edge cases:

- **Invalid port configuration**: `config::load()` returns `Err(ConfigError::..)`
  before any network setup happens. The `?` in `main` propagates this,
  `Box<dyn Error>`'s `Debug` output is printed by the default runtime error
  reporter, and the process exits with a non-zero status. The message
  includes which source (env var or file) was invalid and why.
- **Missing configuration**: both the env var and `config.toml` may be
  absent; `config::load()` returns `AppConfig { port: DEFAULT_PORT }` and
  startup proceeds normally.
- **Port already in use**: `TcpListener::bind` returns an `io::Error`
  (e.g. `AddrInUse`), which is propagated via `?` from `main`, causing the
  process to exit with an error rather than silently picking another port.
- **Unrecognized paths/methods**: not explicitly handled — axum's `Router`
  default fallback (`404 Not Found` for unknown paths, `405 Method Not
  Allowed` for `/` with non-`GET` methods) applies automatically.
- **Concurrent requests**: handled by tokio's async runtime + axum's
  per-connection task model; no additional code required.
- **Host/address**: remains hard-coded to `0.0.0.0` per the approved
  assumption; only the port is configurable.

## Testing hooks for step 6

The structure above is designed so the Test-Definition step can target:

- `config::load()` with controlled env vars / temp config files (unit
  tests for precedence, defaults, and error cases for invalid port values
  in both the env var and the file).
- An integration-style test that starts the axum `Router` (without binding
  a real socket, using axum's `Router` + `tower::ServiceExt::oneshot`, or
  by binding to an ephemeral port) and asserts `GET /` returns `200 OK`
  with body `"Hello, world!"`, and that other paths/methods produce axum's
  default 404/405 responses.

## Out of scope (unchanged from domain spec)

No logging/tracing, persistence, authentication, Docker, or CI are added.
No host/address configuration beyond the port. No graceful shutdown
handling.
