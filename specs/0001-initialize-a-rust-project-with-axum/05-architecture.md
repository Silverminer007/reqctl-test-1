# Architecture

## Proposal

This requirement creates the repository's first application code. There is
no existing `app/` directory, source tree, or build system to integrate
with — the approved tech spec (`03-tech-spec.md`) places the new Cargo
project at the **repository root** (not under an `app/` subdirectory), and
this proposal follows that layout. All files listed below are **new**.

### Files added

```
Cargo.toml          # new — package manifest (binary crate "reqctl-test", edition 2021)
Cargo.lock          # new — generated by `cargo build`, committed
config.toml         # new — example/default config file (port = 3000)
src/main.rs         # new — entry point: load config, build router, bind, serve
src/config.rs       # new — configuration loading/precedence/validation
.gitignore          # replaced — Rust-appropriate entries (/target, .env)
```

No files are modified other than `.gitignore` (wholesale replacement, since
the repo is no longer Go-oriented). No existing application code exists to
change.

### Module layout & responsibilities

- **`src/config.rs`** — owns all configuration concerns, isolated from HTTP
  concerns so it can be unit-tested without spinning up a server:
  - `FileConfig { port: Option<u16> }` — `#[derive(Deserialize, Default)]`,
    mirrors `config.toml`'s shape (`port = <u16>`).
  - `AppConfig { port: u16 }` — the resolved, validated configuration
    consumed by `main`.
  - `ConfigError` — enum with `Env(String)` and `File(String)` variants,
    hand-rolled `Display` + `std::error::Error` impls (avoids adding
    `thiserror`).
  - Constants: `DEFAULT_PORT: u16 = 3000`, `PORT_ENV_VAR: &str = "REQCTL_PORT"`,
    `CONFIG_FILE_PATH: &str = "config.toml"`.
  - `pub fn load() -> Result<AppConfig, ConfigError>` — the single entry
    point `main` calls. Internally:
    1. Attempt to read `CONFIG_FILE_PATH`. Missing file → treat as
       `FileConfig::default()`. Present-but-unparseable (bad TOML, or
       `port` not a valid `u16`) → `Err(ConfigError::File(..))`.
    2. Read `PORT_ENV_VAR`. Unset → ignored. Set but not parseable as
       `u16` (0–65535) → `Err(ConfigError::Env(..))`.
    3. Resolve precedence: valid env var wins → else file's `port` →
       else `DEFAULT_PORT`. Return `Ok(AppConfig { port })`.

  This single function gives the test-definition step (04) a clean seam:
  tests call `load()` directly with controlled env vars and temp
  `config.toml` files (likely via a small internal helper that accepts a
  config-file path / env-lookup override, or by running tests with
  `std::env`/working-directory manipulation — left to the implementation
  step to decide, since 04-tests.md doesn't mandate a specific harness).

- **`src/main.rs`** — composition root:
  - `#[tokio::main] async fn main() -> Result<(), Box<dyn std::error::Error>>`
  - Calls `config::load()?` — any `ConfigError` propagates out of `main`,
    is printed via `Box<dyn Error>`'s `Debug`, and the process exits
    non-zero **before** any socket is touched (satisfies the "invalid
    config → fail fast" edge case).
  - Builds `Router::new().route("/", get(root))`.
  - `async fn root() -> &'static str { "Hello, world!" }` — the
    smoke-test/template endpoint.
  - Binds `TcpListener` to `SocketAddr::from(([0,0,0,0], app_config.port))`
    and runs `axum::serve(listener, app)`. A bind failure (e.g. `AddrInUse`)
    propagates via `?`, again exiting non-zero with no fallback port.

### Data flow

```
process start
  └─ main()
       ├─ config::load()
       │    ├─ read config.toml (optional) ──┐
       │    └─ read $REQCTL_PORT (optional) ──┼─> resolve AppConfig{port}
       │                                       │   (env > file > default 3000)
       │                                       └─ or Err(ConfigError) → exit
       ├─ build Router (GET / -> "Hello, world!")
       ├─ TcpListener::bind(0.0.0.0:port)  ── Err(io::Error) → exit
       └─ axum::serve(listener, router)        # runs until process killed
              └─ per-request: GET / -> 200 "Hello, world!"
                 other path/method -> axum default 404/405
```

### Fit with existing architecture

There is no existing architecture to fit into — this *is* the foundation.
The proposal establishes two conventions intended to carry forward into
future requirements:

1. **Config module pattern**: cross-cutting configuration lives in
   `src/config.rs` with a single `load()` entry point and a typed
   `AppConfig`, returned/extended (not replaced) as new settings are added.
2. **`main.rs` as thin composition root**: route handlers and business
   logic for future requirements should live in their own modules
   (e.g. `src/routes/...`, `src/handlers/...`), wired together in `main.rs`
   — `main.rs` itself stays a short "load config, build router, serve"
   shell. No such modules are needed yet since the only handler is the
   trivial `root` function, which can stay inline in `main.rs` for now.

## Open questions / alternatives considered

- **Location of `root` handler**: Considered putting `root` in its own
  `src/routes.rs` module for "future-proofing," but with a single
  trivial handler this adds an empty layer of indirection without
  benefit. Proposal keeps it inline in `main.rs`; a future requirement
  that adds real routes can introduce a `routes`/`handlers` module then.
- **Config test seam**: 03-tech-spec.md and 04-tests.md specify `load()`'s
  external contract (precedence, error variants) but not how tests will
  control env vars / file paths without inter-test interference (env vars
  are process-global, and `config.toml` path is a constant). Implementation
  (step 10) will need to choose between:
  - Running config tests in a way that's safe with `cargo test`'s default
    parallelism (e.g. serializing the env-var-dependent tests, or using a
    crate like `temp-env`/`serial_test` — which would be a new dev-dependency
    not currently listed in the tech spec), or
  - Making `load()`'s internals (env lookup, file path) injectable via
    private helper functions that the unit tests call directly with
    explicit inputs, leaving the public `load()` as a thin wrapper.

  This proposal does not resolve this now since it's a test-implementation
  detail with no impact on the public `AppConfig`/`ConfigError`/`load()`
  contract or on `main.rs`; flagging it so step 10 doesn't get blocked.
- **`app/` directory**: the task brief for this architecture step refers to
  "modules/files under `app/`", but no such directory exists and
  03-tech-spec.md explicitly places the project at the repository root
  (package `reqctl-test`). This proposal follows the approved tech spec
  (repo root) rather than introducing an `app/` subdirectory, since
  changing the project root would contradict step 5's approved layout.
