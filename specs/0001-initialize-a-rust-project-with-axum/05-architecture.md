# Architecture

## Proposal

This requirement creates the repository's first application code. There is
no existing `app/` directory or source tree to integrate with —
`03-tech-spec.md` places the new Cargo project at the **repository root**
(package `reqctl-test`), and this proposal follows that layout. All files
below are **new**.

This proposal is a fresh pass at step 8, incorporating the user's step-9
feedback on the previous architecture draft:

> "I would like to be able to use env vars in the config file. The config
> file is the source of truth for the application"

Read together, this asks for two things:

1. **The config file is authoritative** — it alone determines the
   application's configuration. There is no separate, independently-applied
   `REQCTL_PORT` environment variable that can override what the config file
   says.
2. **Environment variables can still be used**, but *through* the config
   file — the file declares which env vars feed into which settings (and
   what happens if they're unset), via variable interpolation inside
   `config.toml`.

This is a different config model from the one described in
`02-domain-spec.md` / `03-tech-spec.md` (where `REQCTL_PORT`, if set, always
wins over `config.toml`, as two independent sources with a fixed
precedence). The "Open questions" section below addresses this directly.

### Config file format (`config.toml`)

The shipped default file:

```toml
# config.toml
# `port` accepts ${VAR} / ${VAR:-default} interpolation against the
# process environment. This file is the single source of truth for
# configuration; whether/which env vars matter is decided here, not
# hard-coded in the application.
port = ${REQCTL_PORT:-3000}
```

- A deployment that wants a fixed port regardless of environment writes
  `port = 8080` — no env var consulted, ever, for this setting.
- A deployment that wants `REQCTL_PORT` to control the port (with `3000` as
  fallback) keeps the default `port = ${REQCTL_PORT:-3000}`.
- A deployment that *requires* `REQCTL_PORT` to be set (no fallback) writes
  `port = ${REQCTL_PORT}` — see error handling below for the unset case.

This makes `config.toml` the single declarative source of truth: it fully
determines both the resulting value *and* whether the environment is
consulted at all.

### `src/config.rs`

Data structures:

```rust
#[derive(Debug, Deserialize)]
struct FileConfig {
    port: u16,
}

pub struct AppConfig {
    pub port: u16,
}

#[derive(Debug)]
pub enum ConfigError {
    File(String), // covers interpolation, TOML-syntax, and range errors
}
```

Constants:

```rust
pub const CONFIG_FILE_PATH: &str = "config.toml";
pub const DEFAULT_CONFIG_CONTENTS: &str = "port = ${REQCTL_PORT:-3000}\n";
```

Public entry point:

```rust
pub fn load() -> Result<AppConfig, ConfigError>
```

Internals, split for testability:

```rust
// I/O wrapper: reads the real file + real environment, delegates to the pure core.
pub fn load() -> Result<AppConfig, ConfigError> {
    let raw = std::fs::read_to_string(CONFIG_FILE_PATH)
        .unwrap_or_else(|_| DEFAULT_CONFIG_CONTENTS.to_string());
    resolve(&raw, |name| std::env::var(name).ok())
}

// Pure core: no real I/O, takes an injectable env-lookup closure.
// Unit tests call this directly with literal strings and a fake lookup map.
fn resolve(raw: &str, env_lookup: impl Fn(&str) -> Option<String>) -> Result<AppConfig, ConfigError> {
    let expanded = expand_env_vars(raw, &env_lookup)
        .map_err(ConfigError::File)?;
    let file_config: FileConfig = toml::from_str(&expanded)
        .map_err(|e| ConfigError::File(format!("invalid config.toml: {e}")))?;
    Ok(AppConfig { port: file_config.port })
}

// Hand-written scanner (no regex dependency): replaces ${NAME} and
// ${NAME:-default} tokens with the looked-up env var value, or the
// literal default text, or errors if ${NAME} has no default and is unset.
fn expand_env_vars(input: &str, lookup: &impl Fn(&str) -> Option<String>) -> Result<String, String>
```

Behavior:

- **Missing `config.toml`**: treated as if it contained
  `DEFAULT_CONFIG_CONTENTS` (`port = ${REQCTL_PORT:-3000}`). This preserves
  the domain-spec's "works out of the box, `REQCTL_PORT` still usable"
  behavior without a file on disk, while keeping a single code path (a
  present file with the same contents behaves identically).
- **Interpolation errors** (`${NAME}` with no default and `NAME` unset) and
  **TOML/type errors** (malformed TOML, `port` not representable as `u16`,
  result of interpolation not a valid integer literal) all surface as
  `ConfigError::File(String)` with a message identifying the problem
  (which variable was missing, or what failed to parse).
- There is **no separate `ConfigError::Env` variant** and no direct,
  unconditional read of `REQCTL_PORT` by `main` or `config::load` — any
  influence `REQCTL_PORT` has on the result is entirely mediated by what
  `config.toml` (or the default contents) says.

### `src/main.rs`

Unchanged in shape from the previous draft:

```rust
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let app_config = config::load()?;

    let app = Router::new().route("/", get(root));

    let addr = SocketAddr::from(([0, 0, 0, 0], app_config.port));
    let listener = tokio::net::TcpListener::bind(addr).await?;
    axum::serve(listener, app).await?;

    Ok(())
}

async fn root() -> &'static str {
    "Hello, world!"
}
```

- `config::load()?` propagates `ConfigError::File` before any socket is
  touched — satisfies "invalid config → fail fast, no fallback port".
- `ConfigError` derives `Debug` (in addition to a hand-written `Display` +
  `std::error::Error` impl) so `main`'s default error reporter — which
  prints via `Debug` — shows the actionable message.

### Data flow

```
process start
  └─ main()
       ├─ config::load()
       │    ├─ read config.toml from disk; missing → DEFAULT_CONFIG_CONTENTS
       │    ├─ expand_env_vars(raw, std::env::var)
       │    │     ${REQCTL_PORT:-3000} → "8080" (if set) or "3000" (if unset)
       │    │     ${REQCTL_PORT}       → "8080" (if set) or Err (if unset)
       │    │     (literal `port = 8080` → untouched)
       │    ├─ toml::from_str -> FileConfig { port: u16 }
       │    └─ Ok(AppConfig{port}) or Err(ConfigError::File(..)) → exit
       ├─ build Router (GET / -> "Hello, world!")
       ├─ TcpListener::bind(0.0.0.0:port)  ── Err(io::Error) → exit
       └─ axum::serve(listener, router)        # runs until process killed
              └─ per-request: GET / -> 200 "Hello, world!"
                 other path/method -> axum default 404/405
```

### Dependencies (`Cargo.toml`)

Production:

| Crate | Features | Purpose |
|---|---|---|
| `axum` | default | router + server |
| `tokio` | `full` | async runtime, `#[tokio::main]`, `TcpListener` |
| `serde` | `derive` | deserialize `FileConfig` |
| `toml` | default | parse `config.toml` (post-interpolation) |

Dev-only:

| Crate | Features | Purpose |
|---|---|---|
| `tower` | `util` | `ServiceExt::oneshot` for router tests (04-tests.md §2) |

No regex or templating crate is added — `${NAME}` / `${NAME:-default}` is a
small enough grammar (no nesting, no escaping rules beyond passing through
any `$` not followed by `{`) to scan by hand in `expand_env_vars`, keeping
the dependency set unchanged from the previously approved tech spec.

### Fit with existing architecture / conventions for future requirements

There is no existing architecture to fit into — this *is* the foundation.
Two conventions carry forward:

1. **Config module pattern**: `src/config.rs` owns all configuration
   concerns behind a single `pub fn load() -> Result<AppConfig, ConfigError>`,
   with a pure, injectable `resolve`/`expand_env_vars` core for unit testing.
   Future settings are added as new fields on `FileConfig`/`AppConfig`,
   following the same "config file declares everything, env-var
   interpolation available per-field" pattern.
2. **`main.rs` as thin composition root**: route handlers for future
   requirements live in their own modules, wired together in `main.rs`,
   which stays a short "load config, build router, serve" shell. The single
   trivial `root` handler stays inline for now.

## Open questions / alternatives considered

1. **Conflict with `02-domain-spec.md` / `03-tech-spec.md`'s precedence
   model.** Both documents currently describe `REQCTL_PORT` (if set) as
   *always* overriding `config.toml`, as two independently-consulted
   sources. The step-9 feedback asks for the opposite: the config file is
   authoritative, and env vars only apply where the file says so. This
   proposal implements the step-9 request, which means `02-domain-spec.md`
   §"Configuration sources and precedence" and `03-tech-spec.md`'s
   `load()` precedence rules (and `ConfigError::Env`) are now stale and
   should be updated to match before/alongside implementation. Per this
   step's instructions, I have not edited those files — flagging here for
   the user/maintainers.

2. **Impact on `04-tests.md`.** Several existing test cases assume the old
   two-source model and would need rewriting under this proposal:
   - **1.4 / 1.10** ("env var wins over file value `8080`"): under this
     proposal, if `config.toml` contains a *literal* `port = 8080`, that
     value wins regardless of `REQCTL_PORT` — that's the point of "file is
     the source of truth". These tests' expected outcomes would flip, or
     need to be rephrased as "a literal `port = N` in the file is not
     affected by `REQCTL_PORT`" plus a new test for "a file using
     `${REQCTL_PORT:-N}` *does* pick up the env var".
   - **1.5 / 1.6** (invalid `REQCTL_PORT` → `ConfigError::Env`): under this
     proposal these become `ConfigError::File`, raised when the default
     (or a file using `${REQCTL_PORT:-...}`) substitutes a non-numeric or
     out-of-range value and the result fails to parse as TOML/`u16`.
   - **1.1–1.3, 1.9** (defaults, file-only, env-only, missing file) still
     hold with the same expected outcomes, given `DEFAULT_CONFIG_CONTENTS =
     "port = ${REQCTL_PORT:-3000}"`.
   - A new case is worth adding: `${NAME}` (no default) with `NAME` unset
     → `ConfigError::File` with a message naming the missing variable.

3. **Interpolation syntax**: chose shell/docker-compose-style
   `${NAME}` / `${NAME:-default}` for familiarity and because it requires
   no new dependency (simple hand-written scanner — no nesting, no
   escaping rules beyond passing through any `$` not followed by `{`).
   Alternatives considered:
   - A dedicated config crate (`config-rs`) with built-in env-var layering —
     rejected as a much larger dependency and a different mental model
     (layered sources) than "one file is the source of truth".
   - Mustache-style `{{NAME}}` or bare `$NAME` — rejected as less familiar
     in this context (`.env`/compose-style `${...}` is the closer
     convention) and `$NAME` is ambiguous with literal `$` characters.

4. **Required-but-unset env var (`${NAME}` with no default)**: proposal
   treats this as a hard error (`ConfigError::File`), consistent with the
   domain spec's "invalid configuration → fail to start with a clear error"
   principle. The default shipped `config.toml` always provides a fallback
   (`${REQCTL_PORT:-3000}`), so this only arises if a deployment edits the
   file to require an env var and forgets to set it.

5. **`app/` directory**: as in the prior draft, the task brief's framing of
   "modules/files under `app/`" doesn't match the approved repo-root layout
   in `03-tech-spec.md`. This proposal continues to follow the approved
   tech spec (repo root, package `reqctl-test`).
